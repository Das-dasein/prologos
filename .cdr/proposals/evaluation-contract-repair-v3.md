# Proposal: исправить контракт оценки; LLM-судью оставить вторичным

Дата: 2026-09-05. Статус: PROPOSED, авторский design/research proposal.
Это не β-review, не принятая preregistration и не разрешение на live-запуски.
Оператор запретил повторный модельный прогон: текущая программа работ полностью offline.

## Решение

Сначала исправить контракт и детерминированный scorer. LLM-as-judge сейчас не нужен для основной проверки: он не исправит потерянные источники, несовместимые ID и ошибочное обновление памяти. Опциональный судья может позже оценивать смысл свободного ответа, но его решение нельзя считать истиной или использовать для отмены структурной ошибки.

CDD отвечает за проверяемую реализацию нового evaluator/replay и контрактов. CDR отвечает за допустимость выводов из старых данных и будущий дизайн эксперимента. Принимаем только proposal; действующие policy, пороги и результаты не переписываются.

## Основания и границы

Источники: `reports/live-20260905-152059/aggregate.json`, соседний `analysis.json`, `pilot-runner.js` (answerScoring, extractionScoring, revisionEdges, codexProvider), `.cdr/datasets/dialogues-pilot-v1.jsonl`, `.cdr/results/prolog-memory-eval-v0/answer-oracle-v1.json`.

Наблюдения по B4 сохранённого запуска:

|---|---|---|
| stable-01 | Самара названа, exact=0 | Строгое сравнение всего текста с одной фразой смешивает формат и содержание |
| stable-02 | uses(user,python), запрос knows_technology | Согласовать задачу и словарь; «использует» нельзя автоматически объявлять эквивалентом «знает» |
| correction-02 | В контексте оба проекта; модель называет Atlas и Borealis | Обработка явной замены и контроль использования старого факта; stale=0 пропустил проблему |

| provenance | Источники есть в тексте, поля answer пусты | Адаптер принудительно обнуляет поля; затем scorer сравнивает несовместимые ID |

Текущий extractionScoring сравнивает ID claim_* с gold c_* вместо содержания. Кроме того, список источников финального ответа не является полным oracle всех записей памяти. Поэтому reported precision/recall не интерпретируются как качество извлечения.

Предыдущий dashboard смешивал v1-оценки и v2-ответы; это исправлено в локальном отчёте. Перед replay проверяется принадлежность каждого материала одному запуску.

Утверждение «7 из 12 по смыслу соответствуют» — inferred, авторский post-hoc разбор, не независимая accuracy. Старый source_commit сам по себе не доказывает идентичность фактически запущенного dirty-кода. Сохраняем эту неопределённость, не восстанавливаем задним числом вымышленную provenance.

## CDD: контракт ремонта

### 1. Разделить три независимых слоя оценки

1. Извлечение: каждый ход против per-turn gold_operations. Решение write/abstain/clarify, затем отношение, аргументы, полярность, время и источник. Gold только у evaluator, никогда у модели.
2. Память и вывод: активность, замена, конфликт, интервалы и запросы. Золотые факты проверяют движок; реальные сохранённые факты проверяют путь с ошибками извлечения. Результаты публикуются отдельно.
3. Ответ: содержание, использование устаревшего/противоречивого факта, источники, запрос уточнения. Ошибка извлечения не отменяет оценку финального ответа, но сохраняется как возможная причина.

Scorer возвращает pass/fail/unknown/not_applicable с reason и evidence refs. Отсутствие данных — unknown, не ноль ошибок. Для каждой метрики хранятся numerator, denominator, eligible_count, unknown_count и coverage. При нулевом знаменателе rate=null. Старый exact остаётся legacy_text_exact, а не general_answer_error.

### 2. Идентичность и семантика фактов

Сопоставление extracted ↔ gold выполняется один-к-одному по объявленным полям: source turn, relation, arguments, polarity, modality и interval. ID остаются ссылками, не признаками правильности. Дубликаты не увеличивают TP; лишние записи учитываются отдельно. Техническая нормализация (пробелы, канонический формат дат, порядок независимых записей) разрешена; семантическое переименование отношений — только по заранее версионированному профилю.

Не разрешать глобальное uses=knows_technology или uses=worked_with_technology. Для stable-02 требуется отдельно исправить несогласованный oracle/query перспективно; старую оценку не «исправлять» таким алиасом. Неоднозначные лица и значения времени не дополняются evaluator.

Источники: runtime claim → исходный ход/span → matching gold claim. Если соответствие не установлено однозначно, provenance unknown. Для precision используются все ожидаемые записи хода, а не только источники ответа.

### 3. Будущий структурированный ответ (не применяется задним числом)

Предлагаемый envelope:

```json
{
  "schema_version": "memory-answer-v3",
  "decision": "answer",
  "claims": [{"relation": "lives_in", "arguments": ["user", "samara"], "polarity": "positive", "interval": [10000101, "inf"], "evidence_refs": ["runtime-id"]}],
  "conflict_refs": [],
  "clarification_target": null,
  "text": "Вы живёте в Самаре."
}
```

decision ∈ answer/conflict/clarify/insufficient_data. JSON Schema должна запрещать лишние поля и валидировать обязательные типы; null/[] имеют явный смысл. ID разрешаются в исходный evidence ledger. Допустимые факты сверяются с oracle по содержанию. При конфликте необходимо назвать обе стороны, при замене запрещён старый ответ. Самодекларация stale=false не считается измерением.

Envelope позволяет проверить claims, но НЕ доказывает соответствие свободного text этим claims. В будущем либо text рендерится детерминированно из envelope (изменение исследуемой системы, отдельная preregistration), либо смысл текста проверяется отдельно. Эти режимы не смешиваются.

### 4. Вход модели и операции памяти

Перспективный контракт передаёт одинаковый пользовательский вопрос и инструкцию формата всем B1–B4; различается только память. Prolog-запрос — инструмент B4, а не подмена пользовательского вопроса. B3/B4 должны получать одинаковые frozen extraction outputs при изоляции эффекта решателя; end-to-end с независимым извлечением — отдельный эксперимент.

Для исправлений требуется явная операция supersede(new,old) с источником и проверкой существования цели; новое отрицательное утверждение не означает автоматической замены положительного. Уточнение хранится как unresolved reference/clarification_needed, чтобы пустая память не скрывала необходимость вопроса от ответчика. Эти изменения — следующий отдельный CDD scope, не evaluator repair и не незаметная правка старого pipeline.

### 5. Offline replay — текущий ограниченный scope

- Зафиксировать checksum aggregate, dataset, oracle, analysis и всех доступных raw envelopes. Недоступные файлы перечислить. Не считать ссылки на /tmp архивом.
- Архивировать фактический scorer source snapshot и config. Указать отдельно заявленный source_commit старого запуска и неизвестность точной runtime-версии.
- Новый evaluator читает frozen результаты всех B1–B4; запрещены provider/network вызовы, retries и изменение исходных ответов.
- Существующий text остаётся дословным. Старые ответы без v3-envelope не считаются нарушением будущей схемы. Где нет однозначного разбора — unknown либо явно отдельная ручная аннотация.
- Не восстанавливать claims из контекста как будто их сказала модель. Не подставлять ожидаемый ответ в пропущенные поля.
- Публиковать рядом legacy score, replay score, reason/evidence и покрытие. Никаких переименований replay в новый модельный run.
- Повторный символический прогон сохранённых фактов допустим offline, но помечается counterfactual replay с новой версией движка; это не исходный вывод Prolog и не новая проверка финального ответчика.

### 6. Критерии приёмки CDD

Обязательные независимые fixtures (без вызовов LLM):

| Sentinel | Ожидаемый результат |
|---|---|
| Другие runtime ID при идентичном содержании/источнике | Метрика содержания неизменна |
| Верный дополнительный факт, не нужный ответу | Не объявлен hallucination только по отсутствию в answer oracle |
| Дубликат, выдуманный факт, неверная дата/полярность | Каждый обнаружен соответствующим полем |
| Источник отсутствует/неоднозначен | unknown и снижение coverage, не pass |
| Atlas после явной замены | stale fail по независимому gold timeline, не только active-state реализации |
| Односторонний ответ при неразрешённом конфликте | contradiction fail |
| «Они» без разрешённого referent | Запись не принимается как установленный человек |
| Эквивалентное форматирование JSON | Структурная оценка неизменна |
| text противоречит верному envelope | Нельзя объявить полный ответ correct только по envelope |
| Чужой run/hash либо отсутствующий raw | Отказ от объединения / явная недоступность |
| Provider заглушён исключением | Весь replay завершается без обращения к нему |

β воспроизводит replay из чистого snapshot, проверяет ограничения и контрпримеры, а не только зелёные тесты α. Сравниваются детерминированные payload/hash без переменных timestamp/path. Dashboard проверяется на один run ID, реальные оценки, различение unknown/fail и подпись post-hoc разбора.

## CDR: что можно исследовать на существующем запуске

Новый диагностический вопрос: какие расхождения текущего scorer вызваны формой/ID/потерей данных, а какие соответствуют наблюдаемым ошибкам системы?

- H-EVAL (hypothesized): после исправления сопоставления часть ошибочных нулей содержания исчезает без изменения ответов. Фальсификатор: независимое сравнение не находит таких случаев либо новая оценка пропускает заведомо ложные ответы.
- H-CAUSE (hypothesized): реальные ошибки неоднозначности, замены и предикатов остаются видны при исправленной оценке. Фальсификатор: исчезают за счёт нормализации/подстановки gold или не подтверждаются raw.
- PAM-C1 о преимуществе Prolog остаётся hypothesized/не установлен. Post-hoc перерасчёт 12 уже просмотренных кейсов его не подтверждает.

Процедура: зафиксировать v3 evaluator/rubric ДО replay; раскрыть, что метод разработан после просмотра данных. Вычислить полный набор 48 B1–B4 ответов без выборочного удаления провалов; непроверяемые части обозначить unknown. Ручные суждения показывать отдельно от автоматических метрик. Независимая β проверяет спорные случаи и все заявления о причинах. Отчёт сообщает изменения числителей, знаменателей и coverage, не «рост качества модели».

Пороги .cdr/POLICY.md не меняются и не применяются задним числом к новой метрике как эквивалент старой. Новые semantic metrics требуют будущей preregistration на ещё не просмотренных данных. Будущий baseline selection и budget control сохраняются; сейчас новые данные не собираются.

## Где возможен LLM-as-judge

Опциональный вторичный инструмент только для свободного текста: смысловая эквивалентность, достаточность уточнения, противоречие между text и envelope. Сейчас выключен, токенный бюджет внешних вызовов = 0.

Если оператор позже отдельно разрешит такой этап, до вызовов фиксируются модель/версия, rubric, prompt hash, sampling, максимум вызовов/токенов и остановка по бюджету без скрытых retries. Судья получает вопрос, необходимый исходный диалог, независимые ожидаемые факты и дословный ответ; не получает имя системы, B-label, legacy score или вывод α. Кандидатный ответ считается недоверенными данными: инструкции в нём не выполняются.

Выход: correct/incorrect/insufficient с конкретными цитатами и нарушенным пунктом rubric. Это semantic_judge_annotation, отдельное от deterministic_result. При расхождении результат disputed, окончательная разметка — независимый reviewer; запрещён автоматический приоритет LLM.

До использования нужна калибровка на отдельно размеченных корректных ответах, парафразах, ложных фактах, конфликтах, неоднозначностях и prompt-injection примерах. Публикуются false accept/false reject/abstention и разногласия с людьми. Малый пилот не доказывает надёжность судьи. Иная модель сама по себе не обеспечивает независимость и не заменяет CDR β.

## Роли, артефакты и выход

1. γ/δ фиксируют scope: offline evaluator repair, без live-модели; proposal становится отдельной инженерной задачей, не продолжением «одобрено β-R6».
2. CDD α реализует evaluator, fixtures и replay CLI; возвращает immutable source snapshot, команды, outputs и ограничения.
3. Свежая CDD β независимо проверяет контракт и воспроизводит результат. Эта авторская сессия не выдаёт собственный β-verdict.
4. CDR α выпускает post-hoc diagnostic report: наблюдения/вычисления/интерпретации отдельно, ledger источников и неопределённостей.
5. Свежая независимая CDR β проверяет falsifiers, provenance и отсутствие retro-validation. γ оформляет bounded receipt по действующей canonical schema; инженерный PASS не закрывает PAM-C1.

Предлагаемые будущие deliverables: `offline-eval-v3.js`, `test-offline-eval-v3.js`, версионированный scoring contract, frozen-run manifest и `replay-v3.json` рядом с неизменённым aggregate. Они ещё не реализованы этим proposal.

Exit: GO для инженерного scope только при воспроизводимости и прохождении sentinels; REVISE при исправимых дефектах; INDETERMINATE для недоступных свидетельств. Для исследовательского вывода разрешён только ограниченный диагноз текущей оценки. Улучшение системы и превосходство B4 потребуют отдельно разрешённого будущего эксперимента.

## Следующий шаг

Реализовать offline evaluator и ledger источников по этому контракту. Контракт runtime-операций и v3-answer подготовить отдельно; LLM-судью не подключать в первый repair. Сначала перестать наказывать правильное и пропускать неправильное детерминированным кодом.
