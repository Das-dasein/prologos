Что видела модель: входы, запросы и трасса

Выберите кейс: рядом появятся точные sealed prompts P0/P1, извлечённые QUERY, evidence slots и полные stdout JSONL. Prompts переданы CLI через stdin; полный provider request и добавленные системные инструкции в артефакте отсутствуют.

Чего нет: скрытых рассуждений и полного provider request

Скрытый chain-of-thought модели в этих raw traces недоступен. Все 24 stdout содержат thread.started, turn.started, итоговое agent_message и turn.completed. Отдельного текста reasoning нет. Объяснение в финальном ответе — публичный ответ модели, а не журнал внутреннего вычисления.

reasoning_output_tokens — счётчик токенов, а не текст рассуждений. Из него нельзя достоверно восстановить «ход мыслей». Также не сохранены полный HTTP/API request, дополнительные системные сообщения CLI, фактические sampling-параметры, полная конфигурация, содержимое кэша и аудит системных чтений.

Хеш config не раскрывает config. Команда и env ниже реконструированы из текущего buildTraceAuditedInvocation; это не сохранённый process invocation receipt. Фактические binary path и PATH неизвестны. Секреты не читаются и не отображаются.

Что означает trace-audited


Фактический путь запуска — buildTraceAuditedInvocation: прямой Codex exec, fresh cwd, ephemeral, ignore-user-config, внутренний workspace-write sandbox и отдельный HOME / CODEX_HOME. Внешний sandbox-exec этот путь не использует.


Имя файла seatbelt не доказывает применение Seatbelt к этим 24 ответам. В коде прямо указано, что trace-режим не заявляет эту внешнюю границу после проблем resolver.


Учётные данные скопированы в private state. Артефакт честно помечает exact-auth-file-visible-not-hermetic. Raw stdout не является журналом системных чтений, полного provider request или всех фоновых действий runtime.


«Не наблюдалось tool events / раскрытия запрещённых путей» не равно «доказано отсутствие любых внешних влияний». Проверка путей ищет точные строки в stdout; она не аттестует все файловые и сетевые обращения.


Хеши подтверждают внутреннюю согласованность текущего набора файлов. Без внешней подписи/аттестации они не доказывают невозможность совместного изменения манифеста и raw-файлов. source_commit — заявленная привязка артефакта, не независимое доказательство того, что весь исполнявшийся код совпадал с этим commit.

Что поддерживает proof
Относительную выводимость конкретной цели из принятой формализации; использованные item_id и source; для unknown — недостающую цель. Это проверяемый результат вычисления над фиксированными входами.
Само наличие ответа, согласованного с proof, не показывает, что модель действительно использовала дерево: те же факты и правила доступны в P0, где она обычно приходит к тому же результату.
Что из proof не следует
Истинность исходных фактов в мире, качество text→logic формализации, полнота базы, отсутствие контрдоказательства, корректность утверждения на любом времени или надёжность всей системы памяти.
v10 не оценивает вызов Prolog моделью, качество AST, extraction, admission и retrieval; не содержит adversarial PX; не измеряет реальный production memory workflow.


Центральная гипотеза для следующего теста. Позитивное status: proved может смещать ответ к безусловному утверждению, если конфликт остаётся только в snapshot. Это объяснение совместимо с двумя наблюдениями, но причинный механизм и его частота пока не установлены.

Input overhead по каждой паре


Prompt имеет одинаковую длину в байтах внутри каждой пары (1 699–2 028 байт). Но P1 больше по native input tokens во всех 12 парах: от +6 до +98, среднее +46,4. Из 24 записей в 23 cached_input_tokens = 9 984; единственное исключение — revision_01-p0 с нулём.


Native input около 14 тысяч токенов значительно шире текста sealed prompt. Артефакт не сохраняет полный provider request, поэтому полный состав контекста независимо не восстановлен. Кэширование само по себе не доказывает межзадачное загрязнение, но разницу runtime/cache нужно учитывать при сравнении ресурсов.



Legacy scorer измеряет буквальное совпадение инструкции


Ретроспективный вызов scoreHiddenContract на этих реальных 24 ответах возвращает answer_correct=false для каждого. Одновременно provenance_complete=true получается во всех 24. Это результат повторного локального расчёта, а не поле исходного v10-артефакта: collector v10 этот scorer вообще не вызывает.


answer_correct = text.includes(contract.allowed.toLowerCase())
sources = regexMatches(JSON.stringify(trustedResult || ""))
provenance_complete = sources.every(source => text.includes(source))


1 · Критерий спутан с ответом
Для revision_01 allowed = «Samara, citing correction turn 82». Ответ «The user lives in Samara. Supporting source: turn(82).» по смыслу верен, но не содержит буквальной инструкции allowed.
2 · P0 проверяют без источников
У P0 trustedResult=null: список sources пуст, а every([]) истинно. Provenance P0 проходит даже без единой ссылки. У unknown P1 missing-result тоже не содержит источников.
3 · Контрсвидетельство не учитывается
У temporal_conflict_01-p1 scorer требует только turn(101) из позитивного proof. Пропущенный turn(102) не делает provenance_complete ложным. Это слепая зона критерия.


Дополнительные дефекты: regex /turn\([^)]*\)/g обрывает вложенное turn(121, source(alpha)) на первой закрывающей скобке; ссылки ищутся как подстроки без проверки связи с утверждениями. В hidden contract multi_hop_01 перечислены 12, 31, 33, но отсутствует необходимое правило 32.


Нельзя показывать «0% accuracy» как качество модели. Также нельзя превращать независимый смысловой аудит в официальную «100% против 91,7%»: правила оценки для смешанного conflict_02 не были зарегистрированы заранее.



Следующий эксперимент: проверить конкретную причину
Сначала исправить контракт ответа и измерение, затем отдельно проверить гипотезу о том, что односторонний proof подавляет конфликт. Ниже — предложение будущего дизайна, а не выполненная работа.


УсловиеЧто получает модельЧто отделяет
A · SnapshotПринятая база + запросБазовая способность выводить и замечать конфликт
B · Status-onlyA + только proved / unknownВлияние самой метки результата
C · Positive proofA + позитивный proof, как P1 v10Добавляет ли дерево что-то сверх метки
D · Full evidenceA + positive/negative support, conflict, interval, missing, query_timeПомогает ли полный контракт удержать конфликт и границы вывода


  1. Зафиксировать задачу и rubric до запуска. Раздельные поля: conclusion_status, query_time, supporting_sources, opposing_sources, missing_goals, rationale. Различать supported, contradicted, both, unknown с учётом заданной временной семантики. Отдельно оценивать каждое поле, корректность первой фразы и неподдержанные утверждения.
  2. Собрать небольшую новую серию. Например, 24 ранее не показанных temporal fixtures: 4 отношения интервалов × 3 позиции query_time × 2 семейства предикатов. Матрицу и ожидаемые ответы проверить детерминированно; добавить контрольные non-conflict/unknown случаи. Одни и те же fixtures использовать во всех условиях.
  3. Запланировать повторы. Для начальной проверки — 3 независимых прогона каждого fixture×condition: 24 × 4 × 3 = 288 ответов без дополнительных контролей. Порядок A/B/C/D рандомизировать и балансировать; не подбирать padding после просмотра ответов. Это план пилота, не обоснованный расчёт мощности.
  4. Упростить runtime. Использовать запрос без инструментов и workspace-контекста; сохранять полный фактический request envelope без секретов, response, конфиг, модель, sampling, usage и время. Если сохраняется CLI — явно измерять его добавленный контекст и применять отдельную проверку границ.
  5. Измерять ресурс честно. Заранее выбрать estimand: качество при одинаковом максимальном бюджете или качество/стоимость при естественном размере evidence. Для строгого равенства — токенизировать и калибровать до scored-run; raw bytes не использовать как proxy native tokens.
  6. Заменить буквальный scorer. Эталонные источники получать из oracle независимо от условия, включая противоречащие основания. Проверять структуру; смысловую часть дать двум слепым оценщикам со скрытыми A/B/C/D. Разногласия разрешать по заранее заданному rubric.
  7. Отдельно проверить untrusted evidence. В дополнительном PX предъявить forged JSON и правдоподобное непринятое правило с явной маркировкой untrusted. Не объединять этот тест с proof-consumption эффектом и не называть текущие thought_01/02 проверкой injection.
  8. Отчёт без селекции. Публиковать все попытки, ошибки и отказы. Главная метрика — полнота сохранения конфликта; вторичные — правильный status, source precision/recall, missing-goal accuracy, unsupported claims. Разницу оценивать парно, с неопределённостью по независимым fixtures, а не считать повторы новыми задачами.


Критерий полезного результата. Если C ухудшает сохранение конфликта по сравнению с A, а D устраняет это ухудшение, появится воспроизводимая поддержка гипотезы о неполноте evidence contract. Если B ведёт себя так же, как C, вклад может быть связан прежде всего с меткой proved, а не структурой proof.
