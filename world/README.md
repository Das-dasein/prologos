# Мир агента — PoC v0

Один агент с личной историей, явной целью, обязательством требовать безопасное
доказательство, рефлексией, условным сном и журналом решений. Философский замысел
сохранён в [проекте мира](../.cdd/designs/agent-world-v0.md); эта сборка воплощает
его первый ограниченный эпизод.

## Запустить сцену

Из корня репозитория, при установленных Node.js и SWI-Prolog:

```sh
npm run test:world
npm run world:demo
```

Demo создаёт **новый** каталог `reports/agent-world-<timestamp>/` с HTML-отчётом,
полным JSON и четырьмя независимыми журналами: H1, H2 и их контролями без сна.
Путь печатается в терминале. `npm run world:replay -- PATH/report.json` сверяет
хеши кода, биографию и снимки, затем повторно исполняет сохранённые логические
запросы и ветви. Модель и свободная мысль при таком replay не вызываются.
Для полного demo с отдельной свободной Prolog-мыслью
нужен macOS `sandbox-exec`; проверяемый signed-Horn контур использует SWI как
отдельный процесс и читает программы только как данные.

Ожидаемое поведение:

- H1: старое правило связывает выпуск с резервом → спросить, готов ли резерв.
- H2: старое правило разрешает подтверждённый независимый путь → запросить выпуск.
- В H1 реально исполняются две условные ветви, чтобы выбрать вопрос; в H2 безопасное действие уже доказано baseline, поэтому ветви не запускаются.
- После сна hash принятого знания при том же времени не меняется.
- Ответ «да» в H1 становится отдельным исходным событием и принятым утверждением
  по явной политике бинарного ответа. Перезапуск сохраняет этот опыт.
- Выбор действия ещё не завершает цель: результат поступает отдельным событием
  симулятора. Повторный `step` не выдаёт вторую команду действия.

В демонстрационной H1/H2-сцене простой анализ недостающих предпосылок выбирает
те же действия за одно исполнение вместо трёх. Поэтому обычный `step` использует
`missing`. `dream` остаётся явным исследовательским режимом: сначала предпочитает
вопрос, чья положительная/отрицательная ветвь меняет доступность действия, а
если такого нет — возвращается к обычному допустимому плану вопроса. Это не
сравнительный результат на внешнем датасете и не свидетельство наличия
субъективной Психеи. Ограниченный перебор этого выбора и его границы записаны в
[dream-policy-bounded-search-v3.json](../reports/epistemic-theory-counterexample-v1/dream-policy-bounded-search-v3.json).
Бывший промежуточный witness продолжен до действия в
[dream-policy-trajectory-v4.json](../reports/epistemic-theory-counterexample-v1/dream-policy-trajectory-v4.json): после того как `missing` начал выбирать
кратчайший доступный план, обе policy задают тот же вопрос; dream выполняет
больше проверок. Это единичная траектория policy и стоимости, не оценка
полезности, истинности или модели.

## Продолжить руками

Выберите новый каталог для своего экземпляра:

```sh
npm run world -- init /tmp/my-prolog-world H1
npm run world -- chat /tmp/my-prolog-world
```

Агент спросит о резерве. Ответьте `да`, `нет` или `не знаю`. Доступны `/memory`,
`/history`, `/step`, `/outcome success`, `/outcome failure`, `/exit`.

Отдельные команды для воспроизводимого продолжения разными процессами:

```sh
npm run world -- step /tmp/my-prolog-world dream
npm run world -- answer /tmp/my-prolog-world yes
npm run world -- outcome /tmp/my-prolog-world success 'Симулятор подтвердил выпуск.'
npm run world -- state /tmp/my-prolog-world
```

`init` отказывается перезаписывать существующий журнал. `resume DIR REASON`
возобновляет паузу или прерванную рефлексию с сохранённым расходом бюджета.
Последовательности команд рассчитаны на одного оператора. Запись журнала защищена
блокировкой и проверкой предшествующего hash; это не распределённая транзакционная БД.
Оборванная строка журнала обнаруживается как ошибка, а не молча отбрасывается.

## Модель и свободная мысль

```sh
npm run world -- interpret /tmp/my-prolog-world 'Резерв для orion готов.'
```

Команда использует существующий Codex provider проекта. Она создаёт **кандидат**
и сохраняет точный prompt, ответ модели и объяснение. Выведенный `proposalId`
можно рассмотреть в `state` и отдельно принять:

```sh
npm run world -- admit /tmp/my-prolog-world PROPOSAL_ID 'Сверено с исходным сообщением.'
```

Без модели: `propose DIR TEXT PROLOG` создаёт явное предложение с источником.
Принимать следует после рассмотрения: проверка синтаксиса/поддерживаемого профиля
не доказывает семантическую эквивалентность тексту или эмпирическую истинность.
Неизвестный словарь и неоднозначность могут оставаться без формализации.

`thought DIR FILE GOAL` исполняет **полную неизменяемую Prolog-программу** в
существующем изолированном thought runtime. Рекурсия, метапрограммирование и прочие
возможности Prolog доступны исследованию. В world-профиле запрещено создание
дочерних процессов; сохраняются лимиты времени, стека и вывода. Transcript не имеет полномочий принять
знание или удостоверить вывод. Проверяемый сон — отдельный путь исполнения.

## Общая память и импорт

Новая сборка использует одну проекцию принятого знания для thought и checker.
Существующие `memory-store.js` и `cognitive-memory.js` сохраняют свои интерфейсы.

- `import-assertions DIR FILE TIME` читает assertion-журнал как данные, сохраняет
  исходный архив и создаёт предложение для явно accepted, не superseded/reviewed
  assertions. Полярность и интервалы сохраняются. Отсутствующие/неоднозначные
  квалификаторы не угадываются. Исполняемые directives отвергаются.
- `import-cognitive DIR FILE TIME` сохраняет полный архив cognitive snapshot и
  предлагает его текущую принятую проекцию на TIME. Будущие/истёкшие/замещённые
  элементы перечисляются как skipped. Импорт не восстанавливает доступность
  личного знания до момента знакомства нового агента с архивом.

Это явные адаптеры импорта, а не автоматическая миграция всех старых экспериментов.
Даты в исходной памяти и `TIME` должны иметь один масштаб. В сцене используются
целые логические такты; автоматической конвертации YYYYMMDD в Unix time нет.

## Проверяемая семантика и ограничения

`signed-horn-v0` принимает native Prolog clauses: ground-факты, плоские аргументы,
range-restricted правила с конъюнкцией и независимое отрицание `neg(P)`.
Предметные предикаты декларируются в явной проекции, не зашиваются в ядро.
Не поддерживаются в checker: функции в аргументах, произвольные builtins, `call`,
директивы, факты с переменными, отрицание как неуспех, дизъюнкция и произвольный full
Prolog. Такие программы остаются доступны отдельному thought runtime.

Checker сначала строит raw closure, включая противоположные выводы, затем safe
closure без raw-конфликтующих литералов. Поэтому конфликты не вызывают взрыв,
а независимый чистый путь может поддержать действие. Политика консервативна:
если сам целевой литерал конфликтует в raw closure, действие запрещено, даже
если одна сторона получена через уже конфликтующие предпосылки.

Результат включает provenance-граф с первым найденным доказательством каждого
ground-литерала в каждом из двух контуров, а также `raw_support_sets` и
`safe_support_sets`: все сохранённые по включению минимальные наборы `item_id`
для данного литерала. Первый граф остаётся компактным объяснением; support set
нужны для проверки альтернативных путей. Их число ограничено
`maxProofSupportSets`; при переполнении checker возвращает
`resource_exhausted/proof_support_sets`, а не отбрасывает часть доказательств и
не разрешает действие. Набор support — это происхождение вывода, не
доказательство независимости источников и не решение о допустимости аргумента.
Каждый набор содержит `source_ids` исходных событий и `source_group_ids` —
объявленные оператором или адаптером группы происхождения. По умолчанию группа
равна идентификатору события. Поэтому два альтернативных `item_id` из разных
пересказов одного сообщения могут оставаться двумя формальными выводами, но
аудит показывает общую группу. Совпадение или различие этих идентификаторов —
только наблюдаемая структура происхождения; оно не устанавливает надёжность,
авторитет или реальную независимость людей. Поля `fact_*` и `rule_*` разделяют
происхождение наблюдений и правил: общий policy-source не скрывает различие между
фактами, но и не исчезает из аудита пути.
Оба поля — ограниченные непустые строки; checker отклоняет некорректный
qualifier до запуска Prolog.

Для цели можно явно включить доверенную политику происхождения:

```js
await agent.startGoal({
  id: "release",
  text: "Проверить выпуск.",
  query: "release(orion)",
  action: "request_release_orion",
  actionPolicy: { minIndependentFactSupportPaths: 2 },
});
```

`independent-fact-support-v1` разрешает `act` только при наличии заданного числа
попарно непересекающихся наборов `fact_source_group_ids`. При недостатке таких
путей `WorldAgent` возвращает `pause/insufficient_independent_fact_support` и
сохраняет в decision/reflection канонически выбранные пути или явный пустой
результат. Разные `item_id` и разные источники правил порог не выполняют.
Политика опциональна, сохраняется в goal-журнале и после перезапуска проверяется
по versioned identity. Её `disjoint` означает только различие объявленных групп
происхождения: оператор или адаптер всё ещё отвечает за то, что группы отражают
реальные источники корректно.

Строгая версия добавляет `requireHostAttestedSourceGroups: true` и получает
identity `independent-host-attested-fact-support-v2`. Группа и её assurance
назначаются source-event: строка `sourceGroup` сама по себе имеет assurance
`host_declared`, а `host_attested` требует отдельный
`sourceGroupAttestation: { by, reason }`, который сохраняется в hash-chain.
Обычное событие получает `event_local`. Item-кандидат не может переопределить
группу, assurance или receipt. Поэтому повторная отправка моделью двух
предложений не создаёт два пригодных независимых источника. Старые записи без
этого поля считаются `legacy_unspecified` и строгий порог не выполняют.

Текущая Hermes-конфигурация дополнительно включает
`requireDistinctSourceLineages: true` и получает identity
`independent-host-attested-lineage-support-v3`. Для неё host-attestation должна
содержать `lineage_id`: стабильный идентификатор самого раннего общего
происхождения, которое смог установить адаптер. Две разные группы с одним
lineage не образуют независимую пару; отсутствие lineage также приводит к
`pause`. Это проверка записанной структуры происхождения, а не обнаружение
скрытого копирования или оценка истинности. Подробный контракт описан в
[`source-lineage-policy-v3.md`](../.cdd/designs/source-lineage-policy-v3.md).

Для зависимости конкретных утверждений используется отдельное поле item
`dependsOn`. Если исходный item заменён, истёк или ещё не активен в выбранном
снимке, его явно объявленные производные также исключаются транзитивно. Один
`lineage_id` сам по себе такую зависимость не создаёт: иначе отзыв одного
утверждения удалял бы все утверждения того же источника. Контракт и границы
описаны в
[`assertion-dependency-invalidation-v1.md`](../.cdd/designs/assertion-dependency-invalidation-v1.md).

`datacite-lineage.js` is the first host-side lineage adapter. It parses a
DataCite singleton DOI response, follows an allowlist of explicit ancestor and
`IsIdenticalTo` relations, collapses known identity components, rejects multiple
parents, cycles and oversized graphs, and stores raw responses content-addressed.
`datacite-lineage-cli.cjs` performs the bounded
HTTPS traversal and writes a portable descriptor; it does not create memory
items or admit claims. Example:

```sh
DATACITE_USER_AGENT='my-tool/1.0 (mailto:operator@example.org)' \
node world/datacite-lineage-cli.cjs \
  --doi 10.14454/qdd3-ps68 \
  --receipt-dir receipts/datacite \
  --out reports/datacite-lineage.json
```

The returned metadata can be attached only through the host-side `observe`
boundary. Proposals and admission remain separate.

`compareSupportSets(result, literal, scope)` возвращает попарное пересечение
альтернатив по item, событиям и группам происхождения, отдельно для всех
источников, фактов и правил. Флаги `*_disjoint` описывают только эти множества; они не
являются метрикой независимости людей, качества источника или разрешением act.
Для неизвестной цели возвращаются ограниченные планы недостающих предпосылок
(глубина 16); исчерпание этого поиска не устанавливает невозможность действия.

### Аналитическая проекция аргументов

`world/argumentation.js` — read-only слой для проверки теории, не часть
политики Hermes. Он превращает каждый `(literal, item_ids)` из support sets в
аргумент. Аргумент `B` атакует аргумент `A`, если заключение `B` противоположно
заключению или одному из промежуточных литералов `A`, чья минимальная поддержка
включена в `A.item_ids`. Поэтому отрицание предпосылки может атаковать вывод по
этой предпосылке, а не только противоположный итоговый вывод. Это явно выбранная
support-attack-v0 проекция, а не заявление о полной совместимости с конкретной
системой структурированной аргументации.

`analyzeDung` вычисляет grounded и все preferred расширения полным перебором
для графов до 16 аргументов. Лимит возвращает ошибку `argument_limit` и не
меняет память или выбор действия. [argumentation.test.js](argumentation.test.js)
воспроизводит шестью источниками точный граф из аналитической записки.

`npm run analyze:argumentation-search -- --out NEW_RECEIPT.json` перебирает
1024 сочетания десяти явно перечисленных фактов и правил для `r(orion)`. Это
проверка границы текущей проекции: она ищет расхождения safe/grounded/preferred
без LLM-генерации. Нулевой результат для safe/grounded относится только к этому
конечному базису и не является теоремой о signed Horn в целом.

Лимиты по умолчанию: 2 секунды на query, 1 млн inference steps, 64 MiB stack,
2048 выведенных литералов, 16 384 наборов оснований, 2 MiB вывода; максимум 512 входных элементов. Бюджет
эпизода отдельно считает запросы, ветви и вопросы. До вычисления резервируется
верхняя оценка стоимости, после успешной записи результата неиспользованная часть
возвращается. После прерывания резерв остаётся списанным.

Ценности в этой версии заданы явно: требовать безопасное доказательство,
ограничивать стоимость вопроса и соблюдать бюджет. Автоматическое формирование
ценностей, обобщение опыта, самостоятельное изменение Идей и личности-ветви
остаются следующими исследовательскими и архитектурными шагами.

### Host policy для Hermes

`world/hermes-bridge.js` поддерживает `decide` для явно объявленной цели.
Bridge создаёт или продолжает эпизод `WorldAgent`, вызывает его policy со
стратегией `missing` и возвращает `host_policy_decision`. Ответ всегда помечен
`external_action: not_executed`: host может сформировать simulated action
request, но не выполняет его. Это исключает необходимость просить модель
повторно вывести raw/safe-статус, proof и receipt. Через Hermes provider этот
путь доступен как `world_memory_decide`; он не проверяет, вызовет ли модель
инструмент в произвольном разговоре.
Прямой bridge принимает поле цели `actionPolicy.minIndependentFactSupportPaths`.
Hermes provider берёт этот порог из доверенной настройки
`decision_min_independent_fact_support_paths` в `prolog-world.json` и сам
добавляет к запросу bridge строгую v3-политику с обязательной lineage, поэтому
модель не может ослабить
её, пропустив или подменив поле в tool-call.
